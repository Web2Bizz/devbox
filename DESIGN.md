# Rush Code — DESIGN

Монорепо Rush Code: `apps/frontend` (Next.js 16.3 Turbopack + `@web2bizz/ui`),
`apps/backend` (NestJS API), `apps/mobile` (Expo 57 / React Native 0.86 +
`@web2bizz/ui-native`), плюс `apps/opencode-server` (образ из `apps/opencode-server/Dockerfile`, сервис
описан в корневом `docker-compose.yml`).

Этот файл — **рефера**: общие правила, применимые ко всем UI-приложениями
монорепо. Детальные, специфичные для конкретного приложения правила живут
рядом с ним и здесь только перечислены (см. §0). Если этот файл и
приложенческий `DESIGN.md` расходятся — правит приложенческий (он ближе к
коду и кит-версии).

## 1. Общие принципы

Применимы ко всем UI-приложениям монорепо.

1. **Источник правды — дизайн-система, а не локальные копии.**
   Web: `@web2bizz/ui`. Mobile: `@web2bizz/ui-native`
   (`apps/mobile/packages/uikit`). Компонент кита не дублируется локально —
   либо переиспользуется, либо расширяется в ките. Для mobile это прямо
   закреплено в `apps/mobile/AGENTS.md`: переиспользуемые компоненты живут
   в `packages/uikit`, а не дублируются в `src/components/`.
2. **Токены вместо хардкода.** Литеральные значения цвета допустимы только в
   точке определения темы: `:root` / `.dark` (`apps/frontend/app/globals.css`)
   для web, `packages/uikit/src/theme.ts` для mobile. Всё остальное —
   семантические ссылки (`var(--…)` в CSS, `colors.*` из темы в RN).
   Ветки вида `isDark ? "#hex" : "#hex"` в прикладном коде — признак
   вынесенной темы.
3. **Аккуратность = минимальный дифф.** Правила ниже — про отсутствие
   декора, а не про добавление украшений. Если правило не запрещает явление,
   не добавлять его «для баланса».

## 2. Радиусы и вложенность

**Правило:** `radius(child) < radius(parent)`. Вложенный блок должен
визуально «вписываться» в скругление родителя, а не быть грубее него.

Универсальная шкала уровней вложенности (числовые значения — источник истины
в `apps/frontend/DESIGN.md` §4; здесь только принцип и роли уровней):

| Уровень | Роль                              | Токен (web) |
| ------- | --------------------------------- | ----------- |
| 0 — шелл | Верхний уровень: header/sidebar/content, корневой экран | крупнейший радиус темы |
| 1 — блок | Карточка/секция внутри корня | на ступень меньше |
| 2 — элемент | Элемент внутри блока: badge, button, инпут, вложенная панель | ещё меньше |
| 3+ — мелочь | Чипы, мелкие контролы | минимальный токен темы |

Запрещено:

- `radius: 0` внутри скруглённого контейнера;
- повторять радиус родителя (`var(--radius-lg)` внутри блока, который уже
  `var(--radius-lg)`);
- «flatten»-селекторы поверх кита (позиционирование/ширина/радиус,
  переписывающие то, что кит уже решил). Практический ориентир: если нужно
  переопределить геометрию китового элемента — почти всегда это баг-регрессия,
  а не задача (см. историю `.app-shell > div:has(> .app-header)` в
  `apps/frontend/DESIGN.md` §4).

## 3. Запреты декора

Общие для web и mobile.

1. **Градиенты в блоках запрещены.** `linear-gradient` / `radial-gradient` /
   `conic-gradient` не использовать для фона блоков, карточек, панелей,
   секций. Исключения: бренд-кнопки и текстовый градиент логотипа/вордмарка
   (это текст, не блок). В mobile тема акцента — ровно этот бренд-рамп, и
   он задаётся один раз в `packages/uikit/src/theme.ts`, а не расходится по
   компонентам.
2. **Тени запрещены.** `box-shadow` / `drop-shadow` /
   `filter: drop-shadow` не использовать для блоков и карточек. Исключения:
   фокус-ринги и доступность (`:focus-visible`), а также то, что требует сам
   кит.
3. **CSS-трансформации запрещены как декор.** `transform` / `translate` /
   `scale` / `rotate` / `skew`, `transition: transform` — не применять к
   блокам и карточкам (hover-подъёмы, наклоны и т.п.). Разрешены только
   трансформации, которые требуют доступность или кит (анимации Radix-меню и
   drawer, шелл-шеврон).
4. **Плоский контент.** Вложенные «карточки в карточках» с `border` /
   непрозрачным `background` запрещены: страница линейная — заголовок
   секции, строки/список, разделители, бейджи и кнопки без декоративных
   обёрток.

   Исключения (проверять по смыслу, а не по форме):

   - **карточка данных сущности** — когда `Card` с бордером/фоном несёт данные
     строки (проект, репозиторий, пакет, сессия);
   - **хаб-страница** — групповая страница-каталог, где `Card`-обёртка на
     раздел осмысленна; её листовые страницы снова плоские;
   - **системное сообщение об ошибке** (`Alert variant="destructive"`).

   Не карточка, а пустое состояние / текстовый блок (`Empty`, `EmptyState`) —
   всегда плоский: без `Card`, без бордера, без фона.

## 4. Токены

Конкретные значения (палитра бренда, шкала радиусов, токены геометрии
header, утилиты бренда) — **только** в `apps/frontend/DESIGN.md` §2. Здесь
фиксируется принцип:

- hex/rgb-литералы живут исключительно в точке определения темы;
- бренд-палитра — один источник, от него семантические алиасы (например
  акцент ссылается на первый цвет бренд-рампы), а не копии палитры;
- порядок подключения стилей задаёт source order (кит раньше приложения) —
  менять нельзя, от него зависит каскад (детали: `apps/frontend/DESIGN.md` §1).

## 5. Конвенции по контенту

- **Язык** — `en`/`ru` через i18n-словарь приложения, переключатель в UI;
  язык переживает перезагрузку (cookie в web, хранилище в mobile).
- **URL плоские** — без вложенных route-групп в пользовательском пути,
  без глубокой иерархии страниц.
- **Доступность** — нативные примитивы кита вместо самописных
  (`DropdownMenu`, `Drawer`, `Dialog`): они дают Esc/Tab-ловушку, фокус-ринг
  и корректные `aria-*` из коробки. Собственные виджеты не дублируют эту
  механику. Видимый фокус обязателен.
- **Ошибки** — системные сообщения об ошибке оформляются штатным
  компонентом состояния, а не «карточкой в карточке».

## 6. Владение файлом

- **Владелец — человек.** Агенты читают `DESIGN.md` перед правками UI и
  предлагают изменения, но не переписывают правила молча.
- Порядок работы: агент предлагает правку (с обоснованием, какой пункт
  затрагивается) → человек **approve** → коммит. Правило считается
  принятым только после коммита.
- Новые правила добавляются в приложенческий `DESIGN.md` (если правило
  специфично для приложения) или сюда (если общее для монорепо), с указанием
  причины.
